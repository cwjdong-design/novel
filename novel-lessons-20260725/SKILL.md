# 写作经验与认知（2026-07-25）

## 番茄平台认知

### 核心铁律
1. **番茄奖励「爽」不奖励「好」**。文笔是加分项，节奏是基本盘。
2. **读者耐心=3章**。3章内没打脸→弃书。
3. **每章≥3个爽点**。短剧观众习惯1分钟一个反转。
4. **系统是角色不是计算器**。每5章至少一次「炸屏」——金色字体、成就提示、新数据维度。
5. **主角主动出��**：不是「事情发生在主角身上」，是「主角让事情发生」。

### 爽点配方（五项检查）
- 钱落地：系统钱当场花出去/被配角看见
- 震惊反应：有人不理解 MC 的资源→MC 不解释
- 打脸节奏：被质疑→展示实力→对方闭嘴
- 收入对比：普通人收入 vs 系统收入（数量级差距）
- 系统神秘化：配角察觉异常但无法理解来源

### 广告打断点
- 第3/6/9章章末必须是强钩子（信息截断/视角切换/倒计时型）
- 广告点后第一章开头立刻接上悬念

### 人物配置
- 女性角色必须前5章出场。22岁男主8章没同龄女性 = 致命缺陷。
- 反派冲突前3章就要有摩擦，不能拖到第6章。
- 每章章末作者互动（50-80字，引导评论/投票/追读）

## Claude Code 派发教训

### 派发策略
1. **逐章派发，不批量**。8章一次性=token截断。
2. **输出直存磁盘，不靠日志回读**。`claude -p "..." > /tmp/result.md`
3. **opus 输出必须自动扫描后再人工审查**。opus 会自创：游戏化面板边框、自创地名、自创系统功能（动态上浮/循环状态/外部合作）、自创数字（91.2万人口、不到十八岁年龄）。
4. **铁律必须每次注入**。opus 的记忆在每轮对话中重置。

### delegate_task 红线
- 文字创作任务（DRAFT/POLISH）绝对不用 delegate_task。
- 子代理不遵循铁律→自创地名、数字、系统功能→修复成本远超手写。

## Claude Code 派发教训 v2（2026-07-26）

### 多章派发 = 必翻车
- opus 收到「写3章」指令时，90%概率只输出第一章。
- 解决方案：**逐章派发，绝不批量**。一章一个 `claude -p`，输出直存磁盘。
- 章节编号混乱时：opus 会自创编号（把第12章叫第13章）。存盘前以 `grep "第.*章结束"` 确认只有1个结束标记。
- 文件传参优于内联：中文引号会炸 shell，一律 `cat file | claude -p "$(cat)"`

### 系统面板格式铁律
- 严禁：box-drawing字符（╔══╗）、游戏化边框、动感提示（「冻结」「自动结算」「回报周期预估」）
- 允许：【方括号】格式，静态数据
- 合规示例：外部威胁指数、累计结算金额、渠道数、系数波动、连续运营天数（具体字段和数值由书配置决定）
- 违规示例：动态上浮百分比、循环状态、回报周期预估、关联人口（具体数字）

## 系统设计认知

### 系统记忆点策略
- **第一次炸屏（前期，约第3章）**：破格提示。特殊视觉表现（如暗金色）。结算基准上浮或首次触发主动商业决策的标记。
- **第二次炸屏（前中期，约第5章）**：结算金额跳变（量级突破），让角色和读者都意识到「这不是武器，是大炮」级别的冲击。
- **第三次炸屏（中期，约第7章）**：系统新增统计维度（如「连续运营天数」「累计结算总额」），暗示系统在持续记录，比角色更了解全局。

> 以上章节号为通用参考节奏，实际章号由分卷细纲决定。核心原则是：前期高频炸屏建立认知 → 中期渐变节奏维持新鲜感。

### 系统设计原则
- 每5章给系统加一个新数据维度（不是新功能，是新视角）
- 系统从不主动说话，但数据本身有叙事力量
- 读者通过主角的眼睛看系统，主角的反应=读者的反应

## 写作流程优化

### novel-main 嵌入的技能
- PREP → novel-character（Want/Need 追踪）
- REVIEW → 爽点5项 + 读者审查 + 广告打断点
- TRACK → novel-platform（章末读者互动模板）

### 流程治理 v3（2026-07-26）

#### 根因诊断
8 步全流程不存在「太慢」——是缺少**强制执行机制**。和第 1 轮「写了技能但不用」同源问题：铁律是纸面约束，没被程序化拦截。

#### SOUL.md 入口拦截
- 用户说「写/继续/续写/下一章」→ 强制 `skill_view('novel-main')`
- 禁止跳过：PREP、REVIEW、TRACK（硬性）
- 软性推迟：POLISH/MILESTONE/BACKUP → 每 5 章批处理
- 派发规则：逐章不批量 / 文件传参 / opus 输出验证

#### novel-main 自愈机制
- **DRAFT 前置自检**：自动拉人物卡 + 时间线 + 章节规划 + 最近 3 章正文。即使 PREP 未执行也不缺上下文。
- **REVIEW 自执行**：DRAFT → 自动扫描 → 爽点 5 项 → 读者审查。不输出审查报告禁止进下一章。

#### 本次复盘发现的漏项
| 漏项 | 影响 | 修复 |
|------|------|------|
| PREP 跳过 | 人物状态不一致、时间线断裂 | DRAFT 前置自检 |
| REVIEW 跳过 | 禁用词/地名自创未被发现 | REVIEW 硬性约束 |
| TRACK 跳过 | 前文速查缺失，下一章上下文空洞 | DRAFT 自拉最近 3 章正文 |
| 批量派发 | opus 只能输出 1 章 | 逐章派发规则写入 SOUL |
| MILESTONE 跳过 | 连贯性未检查 | 推迟到批处理，不阻塞写作流 |

### 系统数据驱动铁律（2026-07-26）

#### 根本原则
系统只报数不说话。但每个新数据维度必须立刻触发主角的行动，不能只是「他看了很久」。

#### 三连环规则
```
新数据弹出 → 主角理解含义(≤2句内心) → 立刻行动(下一段就动)
```
反例：「主角看着那个数字，想了很久。然后他转身回屋。」——想了很久但没有行动。
正例：「外部威胁指数偏高。他把纸往桌上一拍——那就简单了。他站起来去找盟友。」

#### 数据→行动密度参考
核心原则：每 2-3 章引入一个新数据维度，且该维度必须触发主角的即时行动（形成闭环）。

| 阶段 | 数据类型示例 | 行动要求 | 闭环标准 |
|------|------------|---------|---------|
| 前期 | 破格提示/结算基准上浮 | 立刻做出关键决策 | 必须闭环 |
| 中期 | 累计统计/外部威胁评估 | 发起应对行动 | 必须闭环 |
| 中期 | 扣款/惩罚性结算 | 调整策略 | 必须闭环 |
| 后期 | 金色结算/量级突破 | 扩大行动规模 | 必须闭环 |

> 允许极少数「只是记账反思」的数据弹出（如中期某章的累计统计），但整本书 85%+ 的数据弹出必须有行动闭环。

#### 未来可用的数据维度设计思路（不违规、只报数）
- 区域性流量/货流量对比（被动统计）
- 用户/客户复购率（被动统计）
- 核心指标按区域/时间拆分
- 系统日结按小时波动
- 异常事件被动标记（只报数据，不判断好坏）

### 读者审查
- 每3章用 opus 以20年网文读者身份审查
- 读者说「想弃」→重写；「想追」→保留结构微调
- 审查标准文件：`references/case-studies/读者审查标准.md`

## 叙事节奏教训

### 前期节奏诊断
- 前数章若无外部冲突（只有内部铺垫）= 番茄死刑
- 正确节奏：第1章系统激活+初步冲突 → 第2章家庭/资源困境+决定行动 → 第3章实地勘察+外部势力首次交锋 → 第4章多线并行+关键人物入场+紧迫deadline
- 每章结束必须有未解决的钩子驱动下一章

### 金句策略
- 番茄爆款每3章至少一句可截屏金句
- 金句来源：长辈的沉默与爆发、精明角色的算计台词、反派被噎住后的沉默、系统结算时主角的内心独白
- 金句要求：脱离上下文也能独立成立，读者截图即可传播
