# 技能解耦方法论：从实例绑定到通用框架

> 来源：2026-08-01 小说创作系统（14个技能、60+文件、616KB→596KB）通用化解耦实践。

## 问题识别

技能在迭代中会自然积累实例特定数据——人物名、地名、数字、路径、平台 ID。这些数据让技能"只服务于一个项目"，无法复用或分享。

### 症状清单

- 方法论中混入特定项目的人物/地名/实体名
- 审查规则中嵌入特定项目的数值公式
- 扫描脚本中写死了白名单/黑名单值
- 创作指导绑定了特定作者的偏好（方言/风格）
- 工具脚本中写死了绝对路径和平台账户 ID

## 解耦铁律

**技能文件只包含通用方法论和流程规范。实例特定数据放在实例自己的数据目录中。**

```
技能文件（通用）              实例数据（特定）
~/.hermes/skills/<name>/     ~/projects/<instance>/
├── 方法论                     ├── 配置文件 ← 技能从这里读取规则
├── 流程规范                   │   ├── 白名单/黑名单
├── 工具脚本（参数化）          │   ├── 字段定义
└── 模板                       │   └── 风格偏好
                              └── 实际数据
```

## 5步解耦法

### 第1步：全量扫描
```bash
grep -rn '<人物名>\|<地名>\|<特定数字>' --include='*.md' <技能目录>/
```
排除目录：`_state/`、`references/`（已有标注的复盘文档）、平台特定工具。

### 第2步：分类——保留 vs 移除

| 类别 | 处理 | 示例 |
|------|------|------|
| 通用方法论 | **保留** | 流程框架、审查清单、评分体系 |
| 通用工具 | **保留+参数化** | 备份脚本、统计脚本 |
| 特定设定 | **移除或占位符化** | 世界观地名、人物状态、面板字段 |
| 特定复盘经验 | **保留但加标注** | "特定项目复盘文档"标签 |
| 平台账户数据 | **参数化** | ID、绝对路径 |

### 第3步：引入配置机制

在实例数据目录中创建配置文件（如 `书配置.md`、`project.config.json`），技能从中读取。

技能文件中引用配置：
```
"从配置文件的白名单字段读取"
"基数 × 系数 × 比例（具体值见配置）"
```

### 第4步：批量修改

大型系统（10+文件）使用 delegate_task 并行处理：
- 按文件大小和复杂度分组（每组 2-3 个文件）
- 给明确的移除清单和保留清单
- 完成后统一 grep 验证

> ⚠️ **重读陷阱**：子任务返回后，父 agent 若基于「之前读取过的旧内容」继续 patch，会覆盖子任务的修改（Hermes 会提示 `subagent modified files the parent previously read — re-read before editing`）。**继续编辑任何被子任务改过的文件前，必须先重新读取**。会话中多次踩中此坑。

### 第5步：零残留验证
```bash
grep -rn '<人物名>\|<地名>\|<特定数字>' --include='*.md' <技能目录>/ | wc -l
# 期望：0
```

## 特殊情况

### 复盘文档（references/）
方法论有参考价值但数据是特定的 → **加标注，不改内容**：
```markdown
> ⚠️ **特定项目复盘文档**：方法论可通用参考，具体数据不具有普适性。
```

### 工具脚本（scripts/）
- 路径硬编码 → `os.path.expanduser("~/...")` 或 `$HOME`
- 数据硬编码 → 从外部 JSON/YAML 配置读取

### 平台发布工具
ID/账户数据 → 命令行参数或环境变量，`config/` 放模板文件

## 关键洞察

1. **技能膨胀是渐进的**——每次"加一个特定项目的规则"都在积累技术债。定期审计（grep 扫描）是必要的。

2. **配置外置化是核心手段**——不是删除特定数据，而是把它移到正确的位置（实例数据目录 vs 技能文件）。

3. **复盘文档加标注而非删除**——实战经验有价值，但需要明确标注"此数据来自特定项目"。

4. **delegate_task 并行处理大型解耦**——14个文件分3组并行修改，耗时3分钟而非30分钟。

5. **grep 验证不可跳过**——修改完成后必须零残留验证，子任务的输出可能有遗漏。

## 开源发布流程（解耦完成后）

> 2026-08-01 小说创作系统 → GitHub 分享完整闭环。解耦是开源的前置条件，但解耦≠可发布。

### 1. 五类零残留验证

发布前 grep 确认以下五类数据全部为 0（排除 `_state/` 运行时目录和已标注的复盘文档）：

| 类别 | 扫描目标 | 示例 |
|------|---------|------|
| 人物名 | 主角/配角/反派名 | 林越、沈知予、阿坤 |
| 地名 | 架空城市/市场/机构 | 穗城、海安、海康 |
| 特定数字 | 人口基数/结算公式/面板字段 | 287341、安居乐业人口 |
| 绝对路径 | `/Users/<user>/` | 硬编码 home 路径 |
| 平台 ID | BOOK_ID/章节ID/账户ID | 7472244177271524376 |

### 2. references 标注复核

复盘文档分两类处理：
- **通用方法论**（零特定数据）→ 保持纯净，无需标注
- **特定项目复盘**（含人物/地名/数字）→ 加标注头，不改内容：
```markdown
> ⚠️ **特定书籍复盘文档**：方法论可通用参考，具体数据不具有普适性。
```
> 子任务审查常发现"漏标注"——批量标注后必须再跑一遍 `grep -L` 找出所有未标注文件，逐一确认是通用还是需补标。

### 3. 基础设施文件

| 文件 | 内容 |
|------|------|
| `LICENSE` | MIT（最宽松，适合技能分享） |
| `.gitignore` | 排除 `_state/`、`__pycache__/`、`browser-profiles/`、`.DS_Store` |
| `requirements.txt` | 可选依赖说明（核心脚本仅标准库） |
| `README.md` | 核心理念 + 路径约定 + 目录结构 + 快速开始 + 安装指南 |

### 4. git 初始化与提交

```bash
cd <技能目录>
git init
git add -A
# 验证 _state/ 等运行时数据未被 add：
git ls-files | grep -i 'progress\|current_book'   # 期望 0
git commit -m "feat: <项目名> v1.0 — <一句话说明>"
```

> ⚠️ **提交前检查**：`git ls-files` 确认运行时数据（进度 JSON、当前书记录）确实被 .gitignore 排除——光靠记忆容易漏。

### 5. 回测验证（解耦后立即做，不等开源）

用户强调"改造不能影响现有工作流"。脚本参数化后必须用**真实项目数据**回测：

```bash
python3 scripts/review_scan.py <真实章节> --book <真实书名>   # config_loaded=True
python3 scripts/consistency_check.py --book <真实书名>         # 7维全通过
python3 scripts/backup_chapter.py <真实章节路径>               # 正常备份
bash scripts/novel_step.sh check <步骤>                        # 流程锁正常
```

> 回测要点：确认 `config_loaded=True`（配置真正被读取）、脚本行为与改造前一致（误报率不增加）。

### 6. 多轮审查

用户明确要求"多轮审查是必要的"。批量改造后的审查闭环：
1. 派 delegate_task 独立审查（搜索残留 → 检查引用一致性 → 确认配置引用完整性）
2. 审查发现的遗漏（如漏标注）立即派发修复
3. 修复后**复检到零**才算完成——子任务自述"完成"不算数，主 agent 必须用 grep 独立验证
