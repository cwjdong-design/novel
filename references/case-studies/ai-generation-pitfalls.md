> ⚠️ **特定书籍复盘文档**：以下内容来源于特定书籍的实战经验，其中的章节号、人物名、地名、数字均为该书的设定。方法论部分可通用参考，但具体数据不具有普适性。

## 一、面板游戏化

opus 会绕过「系统只报数不说话」的约束，通过「美化面板格式 + 增加非说话字段」来间接注入分析/判断。

### 违规示例
```
╔═══════════════════════╗
║  连续运营天数：5天   ║
║  动态上浮：+25%       ║
║  循环状态：资金→收购→渠道 ║
║  回报周期：预估14天   ║
║  外部合作意向：有     ║
╚═══════════════════════╝
```

### 为什么违规
- 表格边框（╔══╗）= 游戏化视觉
- 「动态上浮」「循环状态」「回报周期」= 系统在分析，不是报数
- 「外部合作意向：有」= 系统在判断
- 「预估」= 系统在预测

### 正确格式
```
【安居乐业人口：287,341】
【幸福系数：0.55】
【昨日结算：¥15,803】
```
仅三行。偶尔可加被动统计如「连续运营天数：3」，但不得带任何分析性字段。

## 五、地名幻觉

### 骨架作者自创地名（骨架模式新风险）

实例：Ch23 骨架中写"老周儿子在东莞打工三年"。`东莞` 是真实地名，不在白名单内。opus 忠实执行骨架 → 输出含 `东莞` 3 处 → review_scan 拦截。

**防御**：骨架写完后 grep 扫描真实地名字典。命中即替换为白名单地名或通用描述。
**根因**：骨架作者与 opus 共享现实世界地理知识，大脑自动补全最近的制造业城市。

### opus 自创真实地名

| opus 自创 | Ch | 真实对应 | 类型 |
|----------|----|---------|------|
| 番禺 | Ch21 | 广州番禺区 | 真实区名 |
| 黄埔 | Ch21 | 广州黄埔区 | 真实区名 |
| 海珠区 | Ch21 | 广州海珠区 | 真实区名 |
| 佛山 | Ch21 | 佛山市 | 真实城市名 |
| 中山 | Ch21 | 中山市 | 真实城市名 |

> 根因：opus 训练数据中「穗城(广州)郊区/预制菜产业」与番禺等地名强关联，在描述产业区位时自动调用真实地名词库。
> 防御：review_scan.py 新增 `REAL_PLACE_BLACKLIST` 32词自动拦截。opus铁律明文禁止真实地名。

## 七、Claude Code 创作注意事项

### 1. 自创地名（最高频）
Claude Code opus 会不自觉地创造不在世界观中的地名。例如将「海安」写成「南港」。
→ DRAFT prompt 必须包含铁律：「所有地名必须使用已有世界观中的名称，禁止自创。」

### 2. 角色改名/改身份
Claude Code 可能把「沈知予」写成「苏晴」，把「质检员」写成「采购经理」。
→ DRAFT prompt 传完整人物卡，标注「禁止自行改名或改身份」。REVIEW 后 grep 核验所有人名。

### 3. 时间线描述错误
Claude Code 可能在未经核实的情况下使用相对时间描述，与前章的具体日期冲突。
→ 审查时必须逐章核对所有时间量化描述。

### 4. 人物存活状态错误
Claude Code 可能把活着的人写成已故。→ 审查时确认：任何涉及人物生死的表述是否与人物库一致。

### 5. 数字矛盾
Claude Code 可能给出分项合计与总数不符的数字。→ REVIEW 后人工验算关键数字。

### 6. 抽象抒情
用户偏好用具体意象：「所有灰」而非「所有下午」，「从来不叫人」而非「从来不叫林越」。

### 7. 多章批量派发 → 截断
opus 被要求「分 N 次回复，每次输出一章完整正文」时，经常只输出第 1 章就停止——6-8KB 正文后不再继续。
→ **逐章单独派发**，每个 prompt 只要求一章。每章独立调用 Claude Code CLI，输出直存 `/tmp/chN_output.md`。
→ 不要用 `--max-turns 50` 寄希望于一次输出多章——上下文窗口够大但 opus 不会主动继续。

### 8. 系统面板幻觉（高危）
opus 会自行添加游戏化元素：
- ❌ 面板改成绘图字符边框（╔═══╗）
- ❌ 自创指标：动态上浮 +25%、循环状态、回报周期预估14天、外部合作意向
- ❌ 自创数字：关联人口 91.2万（实际 287,341）、累计结算 ¥126,390
- ❌ 自创系统语言：「系统评级：活跃投放」
→ opus 输出完成后必须跑 review_scan.py + 人工逐行核对所有系统面板。铁律注入不能完全阻止幻觉。

### 9. 文件传参 vs 内联
✅ 可用的文件传参模式：
```bash
cat > /tmp/prompt.txt << 'EOF'
铁律 + 前文 + 章节要求
EOF
claude -p "$(cat /tmp/prompt.txt)" --model sonnet --max-turns 20 --dangerously-skip-permissions > /tmp/chN_output.md 2>&1
```
❌ 不可用的内联模式（中文引号「」会导致 shell 转义失败）
→ 始终用文件传参。输出直存磁盘，不用日志回读。

### 10. 章节编号随波逐流
opus 在批量任务中可能给输出的章节自创编号——把应该输出为「第11章」的内容标成「第13章」。
→ 存盘前永远 run `grep "第.*章"` 核验大标题中的章节号是否匹配。
→ 解决方案：逐章 prompt 中明确写「输出第X章完整正文。以第X章结束结尾。」两个地方写出同一个数字。

### 11. 存盘安全检查
输出中的最后一个标记（如「第13章结束」）必须与文件名（第12章.md）一致。
不一致时→先读正文确认内容对应哪一章→重命名存盘。不要覆盖已有章节。

### 12. 扣款—让读者心疼
系统扣款要达到当日结算额 50% 以上才产生冲击力。扣 3200 当日常结算 25000 → 读者无感。扣 12800 → 读者替主角心疼。
→ REVIEW 时检查扣款数字，低于日结算 50% 的改成≥50%。

## 八、子代理协作陷阱

### 致命失败模式

> 当使用 `delegate_task` 派发子代理处理批量任务（补人物卡、写分卷细纲、补章节规划）时，子代理极易出现两种破坏性行为：

### 1. 擅自改名
子代理将人物库中已注册的角色名改为新名字（如将「沈知予」改为「苏晴」）。子代理会"觉得"新名字更好，完全忽略人物库的权威性。

### 2. 擅自改身份
子代理在未读取人物卡的情况下，基于上下文推测角色身份并写入。写进分卷细纲后，后续所有章节写作都会被污染。

### 防范措施
1. 任何涉及批量文件创建的 delegate_task，必须在 `context` 中写明：**「所有角色名和身份以 `02-设定文档/人物库/` 下的人物卡为准，禁止自行改名或改身份」**
2. 子代理返回后，必须 `grep` 所有输出文件，检查是否存在人物库中未出现的角色名
3. 发现子代理擅自造的角色，立即全量替换并修正相关描述
4. 子代理写入的分卷细纲、章节规划，必须逐行检查涉及角色的身份描述是否与人物卡一致

1. **prompt 层面**：opus铁律注入禁止项 + 关键数字查表 + 系统面板规范

5. **人工核对**：输出后 grep 数字/地名/人名比对铁律

## 十一、文件污染教训

Ch12 重写后，文件被兄弟子agent覆盖回旧版本（阿坤变盟友、威胁1.2面板残留），导致后续patch打在污染版本上。
→ **铁律**：任何通过 tmp 文件 + cp 覆盖的操作，覆盖后必须立即验证 grep 关键数据（数字/人名）是否正确。不依赖「我刚才写了正确的文件」的假设。

## 附录：粤语方言与字数标准

### 粤语方言管控
- 词表限 22 词：搞乜、冇、咩、点解、讲咩、起身、返屋企、边个、边度、唔该、唔知、唔走、未、佢、睇、食、饮、瞓、行、走咗、走佬、饮早茶
- 每章 3-5 处，同一词 ≤2 次，仅限对话引号内
- 不在词表中的粤语禁止自创

### 字数标准
- 番茄标准：2000-3000 字/章，目标 2500 字
- 偏差超过 300 字需调整
