# 技能库维护方法论：解耦 + 架构重构 + 安全协议

> 合并来源：skill-architecture-review.md + skill-decoupling-patterns.md + skill-refactor-protocol.md
> 来源：2026-08-01 小说创作系统架构重构（18 技能统一子目录 + 6 文件瘦身 + 脚本收拢 + references 分类）。
> 用户铁律：大改动必须「调查清楚 → 谨慎优化 → 回测 → 独立审查」，不乱来。

---

## 第一部分：技能解耦——从实例绑定到通用框架

> 来源：2026-08-01 小说创作系统（14个技能、60+文件、616KB→596KB）通用化解耦实践。

### 问题识别

技能在迭代中会自然积累实例特定数据——人物名、地名、数字、路径、平台 ID。这些数据让技能"只服务于一个项目"，无法复用或分享。

### 症状清单

- 方法论中混入特定项目的人物/地名/实体名
- 审查规则中嵌入特定项目的数值公式
- 扫描脚本中写死了白名单/黑名单值
- 创作指导绑定了特定作者的偏好（方言/风格）
- 工具脚本中写死了绝对路径和平台账户 ID

### 解耦铁律

**技能文件只包含通用方法论和流程规范。实例特定数据放在实例自己的数据目录中。**

```
技能文件（通用）              实例数据（特定）
~/.hermes/skills/<name>/     ~/projects/<instance>/
├── 方法论                     ├── 配置文件 ← 技能从这里读取规则
├── 流程规范                   │   ├── 白名单/黑名单
├── 工具脚本（参数化）          │   ├── 字段定义
└── 模板                       │   └── 风格偏好
                              └── 实际数据
```

### 5步解耦法

#### 第1步：全量扫描
```bash
grep -rn '<人物名>\|<地名>\|<特定数字>' --include='*.md' <技能目录>/
```
排除目录：`_state/`、`references/`（已有标注的复盘文档）、平台特定工具。

#### 第2步：分类——保留 vs 移除

| 类别 | 处理 | 示例 |
|------|------|------|
| 通用方法论 | **保留** | 流程框架、审查清单、评分体系 |
| 通用工具 | **保留+参数化** | 备份脚本、统计脚本 |
| 特定设定 | **移除或占位符化** | 世界观地名、人物状态、面板字段 |
| 特定复盘经验 | **保留但加标注** | "特定项目复盘文档"标签 |
| 平台账户数据 | **参数化** | ID、绝对路径 |

#### 第3步：引入配置机制

在实例数据目录中创建配置文件（如 `书配置.md`、`project.config.json`），技能从中读取。

#### 第4步：批量修改

大型系统（10+文件）使用 delegate_task 并行处理：
- 按文件大小和复杂度分组（每组 2-3 个文件）
- 给明确的移除清单和保留清单
- 完成后统一 grep 验证

> ⚠️ **重读陷阱**：子任务返回后，父 agent 若基于「之前读取过的旧内容」继续 patch，会覆盖子任务的修改。**继续编辑任何被子任务改过的文件前，必须先重新读取**。

#### 第5步：零残留验证
```bash
grep -rn '<人物名>\|<地名>\|<特定数字>' --include='*.md' <技能目录>/ | wc -l
# 期望：0
```

### 复盘文档处理

方法论有参考价值但数据是特定的 → **加标注，不改内容**：
```markdown
> ⚠️ **特定项目复盘文档**：方法论可通用参考，具体数据不具有普适性。
```

### 工具脚本处理
- 路径硬编码 → `os.path.expanduser("~/...")` 或 `$HOME`
- 数据硬编码 → 从外部 JSON/YAML 配置读取

### 实战数据（小说创作系统，2026-08-01）

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 技能文件数 | 60 | 60 |
| 系统大小 | 616KB | 596KB (-3.2%) |
| 人物名残留 | 50+处 | 0 |
| 地名残留 | 30+处 | 0 |
| 特定数字残留 | 20+处 | 0 |
| 方言硬编码 | 22词固定词表 | 通用框架（从配置读取） |
| 面板字段硬编码 | 5个固定字段 | 通用占位符 |
| grep 验证 | — | 0/0/0/0 |

### 关键洞察

1. **技能膨胀是渐进的**——每次"加一个特定项目的规则"都在积累技术债。定期审计（grep 扫描）是必要的。
2. **配置外置化是核心手段**——不是删除特定数据，而是把它移到正确的位置（实例数据目录 vs 技能文件）。
3. **复盘文档加标注而非删除**——实战经验有价值，但需要明确标注"此数据来自特定项目"。
4. **delegate_task 并行处理大型解耦**——14个文件分3组并行修改，耗时3分钟而非30分钟。
5. **grep 验证不可跳过**——修改完成后必须零残留验证，子任务的输出可能有遗漏。

## 第二部分：技能框架架构审查与重构方法论

> 前置：先完成解耦，再谈结构重构。解耦解决"内容绑定实例"，架构重构解决"结构不可维护"。

### 触发场景

- 技能库经过多轮迭代后：文件形态混乱、单个文件过大、内容重复、脚本位置分裂
- 准备开源分享前（结构问题会让别人 clone 后跑不起来）
- 用户说"技能要结构化体系化、要有优秀的架构"

### 诊断维度（动手前先调查）

#### 1. 结构统一性：扁平 md vs 子目录 SKILL.md

| 形态 | skill_view 按 name 加载 | skills_list 发现 |
|------|:---:|:---:|
| 子目录 `name/SKILL.md` | ✅ | ✅（出现在可用技能列表） |
| 扁平 `name.md` | ✅（按路径可加载） | ❌（发现层面不可见） |

**核心问题**：扁平技能靠入口技能手动指路，触发链依赖 SOUL.md 硬编码的 `skill_view(name)`。统一为子目录后安全。

#### 2. 文件大小（Hermes 建议 8-15KB）

```bash
for f in *.md */SKILL.md; do echo "$(wc -c < "$f") $f"; done | sort -rn | head
```
> 20KB+ = 警告；40KB+ = 必须瘦身。

#### 3. 重复内容（单一事实源违背）

```bash
find . -name '*.md' | xargs -I{} basename {} | sort | uniq -d
```

#### 4. 脚本位置分裂

- 技能目录 `scripts/` 只有部分脚本，另一部分在 `_shared/scripts/` → 开源时别人 clone 了技能包却跑不起来

#### 5. references 分类不清

- 通用方法论（零特定数据）与特定项目复盘混在同一目录 → 按 `references/general/` 与 `references/case-studies/` 分目录

### 瘦身手法（按性价比排序）

1. **版本历史 → 删除**（历史在 git 里），SKILL.md 加一行「版本历史见 git 提交记录」。
2. **内嵌代码 → 删除**（已外置 .py/.sh 实体），只留「脚本已外置到 scripts/」+ 调用接口。
3. **JSON 格式 / 大表格 → 外置到 `references/general/`**，SKILL.md 只留要点 + 指向。
4. **示例压缩** → 每个概念保留 1 个最典型示例，删重复正反例。
5. **引用共享知识** → 重复词表改为指向 `knowledge/xxx.json`，不复制。
6. **重复的 Fallback/自动化说明** → 汇总为一张「用户交互策略」表。

## 第三部分：安全重构协议步骤

> 用户原话："大改动一定要调查清楚，好好改，不要乱来，谨慎优化然后做回测做审查。"

### 第1步：备份保护（不可跳过）

```bash
git add -A && git commit -m "chore: 重构前备份 — 当前稳定状态"
git tag arch-before-restructure   # 随时可回滚
```

### 第2步：调查（写计划前必须完成）

- 全部技能的 frontmatter 有效性（`head -1` 是否 `---`、name 是否匹配）
- 技能间引用关系图（`grep -o 'novel-[a-z-]*'` 每个文件 → 谁引用谁）
- 外部引用（SOUL.md、cron jobs）——确认改动影响面
- 脚本引用点计数（决定迁移方案）

### 第3步：写详细实施计划

- 每个任务独立 commit、独立回退
- 明确每个文件的瘦身目标和引用替换清单
- 禁止占位符：每个步骤给出精确命令和预期输出

### 第4步：每任务独立 commit 执行

结构迁移（mv → 子目录）、瘦身、去重、引用更新分任务做，每个任务验证后 commit。

### 第5步：脚本路径兼容方案

**最终决策：不保留软链接兼容层。** 软链接有隐患（绝对路径硬编码、换机器即断、双路径语义混乱），且 git 分享时软链接根本不会被跟踪。前提是**先清零所有引用点再删**：

1. 确认引用面：SOUL.md / cron / 其他技能零引用
2. 确认脚本内部互相引用已用新路径
3. 更新执行文档中的旧路径描述
4. 删除软链接 + `rmdir` 旧目录
5. 全链路回测新路径

### 第6步：全量回测（用真实数据，不用样例）

```bash
python3 scripts/review_scan.py <真实章节> --book <真实书名>      # config_loaded=True
python3 scripts/consistency_check.py --book <真实书名>            # 7维全通过
bash scripts/novel_step.sh check <步骤>                           # 流程锁正常
# skill_view 抽查迁移后的技能
```

### 第7步：独立审查（多轮审查闭环）

1. 派 delegate_task 独立审查：结构统一性 / 引用完整性 / 脚本路径一致性 / 瘦身效果 / 硬编码残留 / 配置引用完整性
2. 审查发现的问题立即修复
3. 修复后复检到零；最终 commit + 打 tag

## 第四部分：批量替换要点

- 路径映射批量替换用 python 脚本（old→new dict），排除 PLAN/README（保留历史描述）。
- 替换后 grep 验证残留：核心文件应 0。
- references 分类：通用方法论 → `general/`；含特定书数据的复盘 → `case-studies/`（必须带「特定书籍复盘文档」标注）。

---

## 第五部分：审查必查项（subagent 审查清单）

- 根目录扁平 md 残留 = 0（只留 README/PLAN）
- 空目录 = 0（旧 references 目录要 rmdir）
- 所有 `references/xxx` 引用带 `general/` 或 `case-studies/` 前缀
- 所有 SKILL.md < 30KB
- 核心 SKILL.md 特定书数据残留 = 0
- 脚本绝对路径 / BOOK_ID 硬编码 = 0
- 重复文件 = 0（尤其 knowledge/ 与 references/ 同名）
- 引用的每个文件真实存在

## 第六部分：开源发布流程

> 解耦是开源的前置条件，但解耦≠可发布。

### 1. 五类零残留验证

| 类别 | 扫描目标 | 示例 |
|------|---------|------|
| 人物名 | 主角/配角/反派名 | 林越、沈知予、阿坤 |
| 地名 | 架空城市/市场/机构 | 穗城、海安、海康 |
| 特定数字 | 人口基数/结算公式/面板字段 | 287341、安居乐业人口 |
| 绝对路径 | `/Users/<user>/` | 硬编码 home 路径 |
| 平台 ID | BOOK_ID/章节ID/账户ID | 7472244177271524376 |

### 2. references 标注复核

- **通用方法论**（零特定数据）→ 保持纯净，无需标注
- **特定项目复盘** → 加标注头，不改内容

### 3. 基础设施文件

| 文件 | 内容 |
|------|------|
| `LICENSE` | MIT |
| `.gitignore` | 排除 `_state/`、`__pycache__/`、`browser-profiles/`、`.DS_Store` |
| `requirements.txt` | 可选依赖说明 |
| `README.md` | 核心理念 + 路径约定 + 目录结构 + 快速开始 |

### 4. git 初始化与提交

```bash
cd <技能目录>
git init
git add -A
git ls-files | grep -i 'progress\|current_book'   # 验证 _state/ 被排除
git commit -m "feat: <项目名> v1.0 — <一句话说明>"
```

## 常见陷阱

| 陷阱 | 现实 |
|------|------|
| "迁移后 skill_view 会失效" | 不会——按 name 加载不受文件形态影响 |
| "直接改，别调查" | 用户明确反对。调查清楚是重构的前提 |
| "脚本直接删 _shared 的" | 会破坏 cron/其他流程引用。先清零引用再删 |
| "一次性全改完再验证" | 每任务独立 commit，才能单独回退 |
| 信任子任务的"完成"自述 | 主 agent 必须 grep 独立验证到零 |
